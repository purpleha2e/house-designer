Walkthrough stalls

This is not a release-readiness sign-off. Automatic still-view refinement caused substantial navigation stalls. That work has been removed from normal walkthroughs, but startup time and residual frame spikes remain.

Reproduced cause

The Springfield route covered the landing, bedroom, bathroom, stairs, kitchen, lounge, roof and exterior. Both cutaway-fading controls were disabled. With the previous automatic refinement enabled, the route recorded a 1,447 ms first draw of the refinement texture-readback shader and a worst frame gap of 4,841 ms. Geometry/material preparation continued across camera changes. Progress messages also updated state in the entire house React component.

Changed behaviour

  • The normal menu now offers Build (default) and Lighting preview. Both keep refinement manual. Custom lighting and the refinement controls are under Advanced lighting and diagnostics. The measurements below predate this menu simplification.
  • Refine this view starts optional stationary-view work. Camera movement cancels it; pausing elsewhere does not restart it. Ordinary movement uses the prepared probe lighting.
  • The material-readback shader is compiled asynchronously before its first draw; cancellation after preparation prevents the readback draw.
  • Progress updates subscribe only the two small labels, avoiding house-wide React renders.
  • Automatic bounded performance records distinguish shader preparation, first-use shader draws, slow material draws, explicit texture uploads and long frame gaps. Save performance report exports recent records and settings, without model geometry or textures.

Remaining release blockers

  • The recorded initial shader/material preparation stages took 103.6 seconds in this isolated run. Cold preparation and time to a usable view need their own budget and verification.
  • The worst prepared-view frame gap is still 266 ms. Removing multi-second stalls does not establish smooth performance on target devices.
  • The optional CPU diffuse refinement can still take minutes. It is a still-view tool, not real-time GI suitable for continuous movement.
  • This route covers one furnished project. Broader device, project and editing regressions are still required before a public release.

The evidence identifies application scheduling and first-use GPU work as concrete causes. It does not establish that Three.js is incapable of the intended product, nor that a different engine would make the editor migration inexpensive. A release decision needs measured loading, navigation and editing budgets before further visual features are added.

Validation

Real-house navigation and manual cancellation; real-WebGL readback preparation and cancellation; a React browser test with 20 progress updates and zero host rerenders; focused renderer-health and lighting transport tests; TypeScript, focused lint and production build.
