Product and technical strategy

House Designer production infrastructure

A shared platform for a public home-design experience, professional architectural delivery, manufacturer-managed products, and read-only VR presentation.

Proposal 10 September 2026 Web + WebXR Business model proposal

Executive recommendation

Build one multi-tenant platform with three experiences rather than two separate products: an authenticated designer, a read-only client viewer, and a restricted supplier portal.

Recommended commercial sequence: launch the professional editor and client viewer first, then add the manufacturer catalogue, public configurator, and AI furnishing capabilities on top of the same foundation.
Start here

Professional delivery

Architects, builders, and designers create projects, publish immutable revisions, and send clients a simple read-only link with walk-through and VR controls.

Expansion

Public configurator

Consumers design their homes and furnish them manually or with AI, using only reviewed products from the manufacturer-managed catalogue.

Shared production architecture

The browser remains responsible for interactive editing and 3D rendering. Persistent data, permissions, uploads, and computationally expensive conversion move into managed services.

Current prototype and production gap

The current portal is a useful local development implementation, but it is not a production service. Accounts and catalogue metadata use a local JSON file, sessions are held in process memory, assets are written to one machine, and conversions are spawned as local child processes.

Production therefore needs durable object storage, a shared database, persistent authentication, independent workers, backups, monitoring, and a CDN. The product library should not be bundled into every web-app deployment.

Where assets should live

Keep source files private and publish only reviewed, processed variants. Use immutable versioned paths so a cached headset never receives an unpredictable replacement.

private-originals/
  manufacturer-id/product-id/version/source.glb
  manufacturer-id/product-id/version/source.png

processed-assets/
  manufacturer-id/product-id/version/model-vr.glb
  manufacturer-id/product-id/version/model-desktop.glb
  manufacturer-id/product-id/version/base-color.ktx2
  manufacturer-id/product-id/version/normal.ktx2
  manufacturer-id/product-id/version/thumbnail.webp

private-projects/
  organisation-id/project-id/revision.json
  • Original uploads: private, retained for future reprocessing and never sent to ordinary users.
  • Approved catalogue outputs: normally public through a cached asset domain.
  • Firm-private assets: protected behind authenticated or time-limited CDN access.
  • Project files: private by default and exposed only through project permissions or opaque share records.

Access control is not DRM. Any model delivered into a browser can be recovered by a determined recipient, so licensing decisions should assume that viewers can inspect delivered files.

Production asset pipeline

  1. A manufacturer creates a draft product record.
  2. The API checks their organisation role and issues a short-lived direct-upload URL.
  3. The browser uploads source files into private object storage.
  4. The API records a processing job in a durable queue.
  5. A container worker validates and inspects the source files.
  6. The worker creates VR and desktop GLBs, KTX2 textures, thumbnails, dimensions, polygon counts, and searchable metadata.
  7. Processed outputs are stored under a new immutable asset version.
  8. The product enters administrative review.
  9. Approval publishes that version into the catalogue and CDN.

Jobs should be idempotent, retried after transient failures, and moved to a dead-letter queue after repeated failures. Upload validation should include file type, size, decompression limits, geometry limits, malware scanning, quotas, and ownership/licensing declarations.

Option 1 — public home design

Consumer experience

  • Create, import, save, and share a house.
  • Browse approved catalogue products.
  • Place products manually.
  • Ask AI to furnish selected rooms.
  • Open the design on a headset through HTTPS.

Manufacturer experience

  • Upload and manage only their own products.
  • Supply dimensions, styles, finishes, prices, and product links.
  • Monitor processing and review status.
  • Publish updates as new versions.
  • Receive appropriate aggregated usage or lead analytics.

Catalogue lifecycle

draft → uploaded → processing → review → published → retired

Manufacturers should not publish directly without review. The AI should return placements referencing approved catalogue asset IDs, rather than generating arbitrary unvalidated models. Useful catalogue metadata includes physical dimensions, style, colour, room suitability, mounting type, clearances, price region, availability, and retailer URL.

Commercial observation: this option has strong platform potential but introduces consumer acquisition, catalogue supply, moderation, AI quality, licensing, and high-volume infrastructure at the same time.

Option 2 — professional editor and client viewer

Each architecture or construction business becomes an isolated organisation containing its users, projects, private assets, published revisions, and client shares.

Authenticated designer

  • Create and edit cloud projects.
  • Use the global catalogue and firm-private assets.
  • Invite colleagues with organisation roles.
  • Publish a deliberate, immutable client revision.

Read-only client link

  • No modelling or material-editing controls.
  • Simple orbit, walk, floor, and VR controls.
  • Optional expiry, passcode, email gate, or revocation.
  • Optional practice branding and project information.

A share such as https://view.example.com/s/7Dk3mP9x should resolve to a published project revision. Continuing design work must not silently change what a client sees; the designer explicitly republishes when a revision is ready.

The “single link” should be a hosted experience, not one enormous HTML file. The viewer downloads a small project document and only the immutable CDN assets used by that project. An offline archival export can be added later if firms require it.

Identity, permissions, and data model

Use organisation membership and roles rather than embedding permissions in UI logic. Database-level tenant policies should enforce who can read or change each record.

Catalogue visibility should support public, organisation, and private. Manufacturers publish global products; approved staff at architecture firms may upload private bespoke assets; clients and ordinary public users receive no upload capability.

Suggested delivery roadmap

  1. Phase 1Cloud foundation: managed identity, PostgreSQL, cloud project saving, object storage, and HTTPS deployment.
  2. Phase 2Professional release: organisations, project roles, immutable publishing, read-only links, and reliable VR delivery.
  3. Phase 3Asset service: direct uploads, durable queue, container conversion, validation, versioning, and firm-private libraries.
  4. Phase 4Manufacturer network: supplier onboarding, product review, global catalogue, lifecycle management, and analytics.
  5. Phase 5Consumer and AI: public accounts, guided design, catalogue-based furnishing, product recommendations, and lead generation.
Why this order works: the professional product validates the core editor, publishing model, asset delivery, permissions, and VR experience with a smaller population of identifiable paying customers. The same services then support the larger public product.

Immediate technical priorities

  1. Define organisation, project revision, share, product, and asset-version schemas.
  2. Replace local project files with a cloud project API while retaining JSON import/export.
  3. Move models and textures out of the application bundle into versioned object storage.
  4. Containerise the current GLB/KTX2 conversion scripts and make processing idempotent.
  5. Add manufacturer and administrator roles with an approval workflow.
  6. Create a dedicated read-only viewer route and publish operation.
  7. Measure headset load time, memory, texture use, triangle count, and frame rate as release gates.
