# Accounts and private workspaces

The first implementation is a runnable **local development foundation**. It
provides registration, sign-in/out, persistent sessions, one private workspace per
account, storage allowances and private file upload/download/deletion. Local
editing and device-file saves continue to work without an account.

Open **Project menu → Account & workspace** in the editor. An account created here
is a development account on the computer running the service. The dialog says
this explicitly; it is not a hosted cloud account.

## Run locally

Use Node 24 or later. No Java installation or new npm dependency is required.

```powershell
npm run dev:all
```

This starts the editor, existing asset portal and the new account/workspace
service. Alternatively, run `npm run dev` and `npm run dev:workspace` in separate
terminals. `npm run preview` also starts the local workspace service if it is
not already running. Vite proxies `/api/workspace` for both development and
preview. `npm run preview:vite` serves only the editor and needs a separately
started workspace service.

The workspace service listens only on `127.0.0.1:5175`. It stores its SQLite
database and private files in `.workspace-data/`, which is excluded from Git.
Accounts and files persist when the service restarts. Back up that directory to
keep this development data; this implementation does not provide cloud backups.

The account dialog is for registration, sign-in/out and storage usage. It is not
an upload centre. Workspace saving belongs in the house Save flow, material
creation and object import flows; those integrations are the next step. Each
flow will offer private workspace storage, with explicit community publishing
added later. Device-file saves remain available.

The underlying private storage API accepts house JSON, portable material JSON
and GLB objects (100 MiB per account/file by default). It is available for those
integrations and covered by API tests, but is not exposed as a generic account
screen upload form. Stored files are not yet published tours or catalogue entries.

Optional environment variables:

| Variable | Purpose |
|---|---|
| `WORKSPACE_PORT` | Local API port; defaults to `5175` |
| `WORKSPACE_TARGET` | Vite's API proxy target; defaults to `http://127.0.0.1:5175` |
| `WORKSPACE_DATA_DIR` | Database and object-storage directory |
| `WORKSPACE_QUOTA_BYTES` | Storage allowance assigned to newly created workspaces |
| `WORKSPACE_MAX_UPLOAD_BYTES` | Per-file upload limit; at most 250 MiB |
| `WORKSPACE_ALLOWED_ORIGINS` | Comma-separated editor origins; default localhost/127.0.0.1 on ports 5173, 4173 and 5180, HTTP or HTTPS |

Run one service process per database directory. The CLI deliberately refuses
`NODE_ENV=production`: local development password accounts are not a substitute
for hosted identity, verification, recovery and production session management.
No Supabase or Cloudflare resources are created by these commands.

## Boundaries already in place

- Account IDs and workspace IDs are generated by the server. Requests never
  choose the owner of an upload. A known file ID cannot bypass ownership checks.
- Private object paths are generated from server IDs. Arbitrary paths and
  directory names are rejected; there is no public file-serving directory.
- Local development passwords use salted asynchronous scrypt. Only a hash of
  the random session token is stored, and the cookie is HttpOnly and SameSite
  Strict. Logging out revokes the stored session. Account responses contain no
  password material or session tokens.
- Mutations require the editor's request header. Browser origins are checked
  against an explicit list, without trusting forwarding headers for rate limits.
- Upload reservations count towards the allowance before bytes are written.
  Failed/incomplete writes never appear as saved files. Interrupted operations
  are cleaned up before the service starts accepting work.
- `WorkspaceObjects` isolates file storage. `WorkspaceStore` describes the API's
  account/workspace operations and can be supplied to the HTTP service, allowing
  hosted implementations without rewriting the editor dialog.

## Hosted direction

Recommended starting stack: **Supabase Auth and Postgres** for hosted identity,
ownership and publishing records; **Cloudflare R2** for materials, objects and
published tour files. These are recommendations, not configured integrations.

The hosted service should validate identity, allocate each user's workspace,
enforce ownership and allowance, and authorise narrowly scoped uploads. Only
validated uploads become ready assets. The local account database is disposable
development data; production users register with the hosted identity provider.

Next steps, in order:

1. Connect hosted registration/sign-in, verification and recovery, and implement
   the workspace store in Postgres with ownership policies and atomic allowance
   reservations. Configure R2 and a deployment for the service.
2. Connect **Save to workspace** to house saving, material creation and object
   import. Keep account settings separate from these content workflows. Preserve
   local/offline copies and stable asset versions.
3. Publish a complete versioned tour snapshot and return a stable share link.
   Validate dependencies and saved lighting before activating the new version.
4. Add explicit community submission and approval, search, previews, download,
   attribution and reuse permissions. Publishing a tour does not automatically
   list its private assets in the community catalogue.

A shared tour must deliver its rendering assets to viewers. Keeping an asset
out of the community catalogue does not make its bytes secret from tour viewers.
Community listing, reuse permissions and editable-project downloads need
separate controls.

## Verification

```powershell
npm run test:workspace
npm run build
npm run test:workspace:browser
```

The browser check starts its own isolated Vite/workspace services on unused
loopback ports and a disposable Chrome profile. Set `CHROME_PATH` if Chrome is
installed elsewhere. API tests cover ownership isolation,
session persistence/expiry/revocation, upload validation, concurrent allowance
enforcement, failure/restart recovery and authentication rate limiting.
